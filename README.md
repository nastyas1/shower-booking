**Shower Booking System** — это автоматизация бронирования душевых кабинок в общежитиях, фитнес-центрах и гостиничных комплексах. Проект представляет собой **модульный монолит**, разделенный на независимые логические слои. 

## Ключевые возможности

### Для Пользователя (Мобильное приложение)
- **Авторизация и безопасность:** Регистрация и вход по JWT-токенам.
- **Просмотр расписания:** Интерактивный календарь со свободными слотами.
- **Бронирование:** Выбор кабинки и времени с защитой от двойного бронирования.
- **Личный кабинет:** Просмотр своих броней, возможность отмены.
- **Обратная связь:** Отправка заявки о неисправности.

### Для Администратора (Веб-интерфейс Django Admin)
- **Управление кабинками:** Добавление, редактирование и блокировка кабинок в системе.
- **Управление пользователями:** Блокировка нарушителей.
- **Обработка заявок.** 

## Технологический стек

### Backend
- **Язык:** Python 3.11+
- **Фреймворк:** Django + Django REST Framework (DRF)
- **База данных:** PostgreSQL 16 (локальный запуск)
- **Аутентификация:** JWT
- **Документация API:** Swagger

### Mobile
- **Фреймворк:** Flutter (Dart)
- **Платформа:** Android (сборка APK)

Исходный код мобильного приложения находится в `mobile/`. Для запуска нужны
Flutter SDK и Android SDK:

```bash
cd mobile
flutter pub get
flutter test
flutter run
```

Для эмулятора Android по умолчанию используется API `http://10.0.2.2:8000/api/`.
При необходимости задайте другой адрес через
`--dart-define=API_BASE_URL=http://<host>:8000/api/`.

Экран расписания получает активные кабинки и свободные интервалы через
`GET /api/cabins/available?date=YYYY-MM-DD`; даты и время отображаются в часовом
поясе, который возвращает API.

Мобильный клиент использует `POST /api/auth/register/` с полями `username`,
`email` и `password` для регистрации, `POST /api/auth/token/` с `username` и
`password` для входа, а также `POST /api/auth/token/refresh/` для обновления
access-токена. Успешные ответы регистрации и входа содержат строки `access` и
`refresh`. Защищённые операции принимают access-токен в заголовке
`Authorization: Bearer <access>`.

`GET /api/bookings` возвращает брони текущего пользователя в формате
`{"bookings":[{"id":1,"cabin_number":"A-01","starts_at":"...","ends_at":"..."}]}`.
Отмена выполняется запросом `DELETE /api/bookings/{id}`; этот endpoint будет
добавлен отдельной задачей.

Форма неисправности отправляет `POST /api/maintenance` с полями `cabin_id` и
`description`; endpoint уже доступен и требует Bearer access-токен.

## Архитектура проекта

**Бэкенд разделен на независимые приложения (apps):**
- **`users`**: Аутентификация (JWT), профили, разграничение прав (Пользователь/Администратор).
- **`cabins`**: Управление кабинками.
- **`bookings`**: Ядро системы. Логика расчета свободных слотов.
- **`maintenance`**: Обработка заявок на ремонт.

**Мобильное приложение (Flutter) разделено на слои:**
- **`presentation`**: Экраны и виджеты.
- **`data`**: Работа с API и сохранение токенов.
- **`models`**: Модели данных.

## Локальный запуск backend

Требуются Python 3.12+ и локальный PostgreSQL. Выполните команды из корня репозитория:

```bash
cd backend
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Сгенерируйте ключ командой ниже и скопируйте его в `SECRET_KEY`. Заполните
`DB_NAME`, `DB_USER` и `DB_PASSWORD` в `backend/.env` значениями для вашей
локальной среды. Создайте в PostgreSQL базу с именем из `DB_NAME`, затем
выполните миграции и запустите сервер:

```bash
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
python manage.py migrate
```

Для заполнения локальной базы тестовыми кабинками, пользователями и
администратором укажите `SEED_ADMIN_PASSWORD` в `backend/.env` и выполните:

```bash
python manage.py seed_data
```

Если нужен вход демо-пользователями, задайте им локальный пароль через
`SEED_USER_PASSWORD` в `backend/.env` до запуска команды. Без него новые
демо-пользователи создаются с отключённым паролем. Повторный запуск команды
не сбрасывает пароли существующих записей и не создаёт дубликаты.

Затем запустите сервер:

```bash
python manage.py runserver
```

Часовой пояс и ежедневный интервал работы задаются переменными `TIME_ZONE`,
`OPERATING_OPEN_TIME` и `OPERATING_CLOSE_TIME` в `backend/.env`. Если время
закрытия не позже времени открытия, интервал заканчивается на следующий день.

### Доступность кабинок

`GET /api/cabins/available?date=YYYY-MM-DD` возвращает активные кабинки со
свободными интервалами на выбранную дату. Интервалы учитывают существующие
брони и открытые/выполняющиеся заявки на ремонт. Даты и время ответа используют
настроенный часовой пояс.

Авторизованный пользователь может отправить заявку на ремонт через
`POST /api/maintenance` с JSON-полями `cabin_id` и `description`. Новая заявка
создаётся со статусом `open`; пока заявка открыта или выполняется, кабинка
исключается из расписания и для неё нельзя создать бронирование.

### Панель администратора

В `/admin/` доступны списки пользователей, кабинок, броней и заявок на ремонт
с поиском, фильтрами и сортировкой. Для выбранных заявок администратор может
выполнить массовое действие «Resolve selected requests and release cabins»:
заявки закрываются, и доступность кабинок пересчитывается по их статусу.
Кабинки, отдельно помеченные неактивными, при этом не активируются.

Главная страница админки показывает статистику за операционный интервал
текущей даты: число броней, число активных кабинок, активные кабинки хотя бы
с одной бронью и процент загрузки. Процент рассчитывается как доля таких
занятых кабинок от числа активных; если активных кабинок нет, загрузка равна
нулю.
